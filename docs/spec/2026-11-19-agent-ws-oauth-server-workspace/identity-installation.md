# OAuth Machine Identity and System Installation

## Better Auth integration

Each server has an OAuth machine identity. Administrators use their Better Auth sessions to authorize enrollment, rotation, and revocation. The agent starts with its own credentials and continues operating after the administrator signs out. Use the pinned OAuth Provider 1.7.25 and the existing JWT and JWKS setup. The pinned package types include `client_credentials`, admin client creation, machine scope ceilings, and machine access-token lifetime. Verify issuance and database adapter behavior in the first identity implementation change. [Better Auth client management](https://better-auth.com/docs/plugins/oauth-provider/clients) · [Token and resource configuration](https://better-auth.com/docs/plugins/oauth-provider/tokens)

- Register a dedicated agent resource derived from the canonical public control-plane URL and add the `blossom:agent:connect` scope. Link each agent client only to that resource and restrict it to `client_credentials`, `client_secret_basic`, and the machine scope. Only the authorized server-side enrollment logic can create these clients. Before enforcing per-client resources, backfill the MCP resource link for existing MCP clients and verify the default resource for dynamic registration. Preserve MCP registration behavior and existing clients' access-token lifetimes. Test that dynamic registration, user-managed clients, and MCP tokens cannot gain agent permissions.
- Add an `agent_identity` record with a unique OAuth client ID, server ID, status, generation, creation and revocation timestamps, and operator. Allow one active identity per server and one pending identity during replacement. The Better Auth token endpoint receives the resource and scope, with a proposed token lifetime of 15 minutes. Deliver the client secret once and use the provider's hashed secret storage.
- At upgrade, validate the token using the configured issuer and JWKS. Check the signature, validity period, exact audience, scope, and provider-issued machine client identifier. Look up its active identity and server status. Fix the client identifier claim name in integration tests against actual provider output. Derive the server ID from the identity mapping. Agent OAuth authorizes the machine channel and the agent's own server data. Admin operations, browser relay, and MCP enforce their respective permissions.
- Before token expiry, obtain a fresh token through the same grant and reconnect over WSS. Use a planned reconnect in the first release and show the remaining connection time in the terminal. The session deadline is the earliest of the lease deadline, platform limit, and token expiry. Send revocation or access changes through the hub and check the authoritative state every 30 seconds as a fallback. Close the connection if revalidation fails. Durable writes still check the current identity and session. On authentication failure, keep the local proxy running and surface the need to reauthorize.
- Validate static tokens with the existing hash lookup. Place them in the backup credentials area on the Connection tab. Existing servers continue using their token until migrated. After switching to OAuth, administrators can disable, rotate, or reauthorize the backup token. The installer defaults to OAuth, and the agent uses the explicitly configured authentication mode even when OAuth is rejected.

## Per-server installer

| Operation | Proposed interface and authorization |
| --- | --- |
| Create an enrollment grant | Audited admin POST server function using `ensureAdmin()` and `adminAudit(...)`. Bind the grant to the server ID, mode, enabled capabilities, selected release, and expiry. Require explicit confirmation for reinstallation or credential replacement. |
| Download the script | Same-origin admin GET `/api/admin/servers/<id>/installation/script/<grantId>`. Validate the admin session and grant ownership and return an attachment with `private, no-store`. The script contains the target server's connection parameters and the fixed installation logic. |
| Redeem the grant | The agent sends an HTTPS POST to `/api/agent/enrollment/redeem` with the one-time grant in the request body. Resolve the server ID from the grant record, verify server status and expiry, and check that the grant is unspent. The grant limits the resulting identity to the target server. |
| Confirm installation | The new agent authenticates with OAuth, synchronizes its first configuration over WSS, and acknowledges the applied version. The workspace shows grant created, redeemed, connected, configuration applied, or failed. |

The script can be regenerated, and the enrollment secret is delivered once. The creation action may return a complete one-time download with the secret. Alternatively, download the script and enter the secret interactively on the host. Subsequent GET requests return the script without the secret. Proposed grant lifetime is 15 minutes. Store only its hash and allow administrators to revoke it. Deliver the script and grant through an administrator-controlled channel and run the installer once on the target host. Keep grants and client secrets out of process arguments, URLs, shell history, logs, and audit records. Restrict files containing plaintext to the owning account.

Atomically claim an unspent grant before creating a client. If provider registration and the business mapping cannot share a transaction, mark the grant as redeeming and create a traceable pending record. Allow pending identity handshakes only after completing the binding. Use the attempt ID to clean up or revoke orphaned clients and resource links on failure. Persist the attempt status and identifier, and deliver plaintext credentials only in the successful response. If the response is lost or the agent cannot save the credentials, an administrator revokes the pending identity and issues a fresh grant. Retries cannot retrieve the secret. Concurrent or expired attempts cannot replace the active identity. On a first installation, promote the identity on its first successful handshake. During rotation, the pending identity can verify connectivity and credentials. Once the switch is confirmed, atomically activate the new generation, close the old connection, and synchronize. A failed rotation leaves the original credential and running proxy available.

## Linux systemd installation

1. Verify Linux, amd64 or arm64, systemd, required tools, and administrator permissions. Check the existing service, directories, version, and server binding. Allow a safe rerun when the binding matches. Require an explicit choice for conflicts or reinstallation. Container deployments use the existing entry point.
2. Download pinned agent and compatible sing-box releases from configured sources. Verify version, architecture, and trusted digests. Agent releases already include SHA256SUMS. The grant pins control-plane-trusted digests, so a mirror used for downloading cannot supply a new expected digest. Artifact signing can follow separately. Verify staged artifacts before activation.
3. Create a dedicated non-root service account and restricted configuration, credential, and state directories. Grant only the bind capabilities needed by the configuration and prefer high ports. Derive the control-plane URL from trusted configuration and render the script from a fixed template with safe parameter encoding. The agent saves credentials locally in a file with mode `0600`. Replace configuration and service definitions atomically, with distinct working and state directories.
4. Enable and start the service through systemd and honor the agent's restart exit behavior. On failure, retain diagnostics and roll back the binaries and unit activated by the attempt. Reuse existing proxy configuration, certificates, traffic queue, and credentials during rollback. Provide service status and uninstall instructions. At uninstall, let administrators choose whether to remove local state and revoke the control-plane identity.

Treat server names, notes, and other free text as data throughout script generation. Report the local systemd service state separately from the first configuration acknowledgment received by the control plane. During network failures, display the last known status and the available enrollment recovery action.
